## 1. AI 介入环境与核心价值

### 1.1 版本演进（事实）

| 阶段 | 说明 |
| --- | --- |
| v1.0.1 起 | AI 分析采用**前端浏览器本地直连大模型**架构并持续至今；早期后端遗留的 AI 存储表（ai_analysis）已随升级脚本移除（见 db/upgrade.sql 注释），现版本后端**不含任何 AI 调用逻辑与 AI 数据存储** |
| v1.1.0 | “AI 设置”页成型：常用服务商下拉、自定义 OpenAI 兼容地址、模型列表自动拉取 |
| 现行 v1.3.0-beta.1 | 三个 AI 场景 + 设置/历史管理完整可用，配置与历史均存本机浏览器（详见 frontend/src/utils/ai.js、AI-CONFIG.md） |

### 1.2 AI 介入的三个场景与数据流

系统在“管题—练题—分析”闭环的三个**人工工作节点**提供 AI 辅助，全部由**用户主动点击触发**：

**场景 A：批量导入时的答案/解析补全**（对应 frontend/src/components/ImportDialog.vue）
- 介入环节：批量导入向导第 2 步“预览校验”后。
- 流程：用户勾选缺失答案/解析的行（单次上限 50 行）→ 点击“AI 补全”→ 大模型按结构化要求返回 `{"answer": "...", "analysis": "..."}` → 结果写入预览表格单元格（**仍可人工逐行修改**）→ 用户确认后第 3 步入库；未成功的行提示“AI 未能补全: 第 X 行(可手动在库中补充)”。
- 数据流：当前行题目文本（题干/选项/标签）→ 用户配置的服务商；响应仅回填预览，不直接写库。

**场景 B：单题质量分析**（frontend/src/views/QuestionsView.vue）
- 介入环节：题目列表每一行的“AI 分析”按钮。
- 流程：点击后发送该题文本（含参考答案与解析）→ 要求输出四段：①考查知识点 ②难度评估(1-5)及理由 ③表述清晰度与改进建议 ④解题思路提示（**提示词明确要求不直接给出完整答案**，防刷题作弊）→ 弹窗展示，不写入题目、不修改任何业务数据。

**场景 C：个人学情报告**（frontend/src/views/DashboardView.vue）
- 介入环节：统计看板“AI 学情报告”按钮。
- 流程：前端将**当前页面统计摘要**（题目总数/练习次数/错题数/总正确率/错题最多的分类/近两周练习趋势等数字与分类名）组装为提示词 → 要求输出：总体表现评价 / 薄弱知识点分析 / 具体学习建议 / 后续练习计划建议 → 弹窗展示。报告为一次性生成，仅存于本机浏览器本地历史，**后端不落库**。

**通用支撑设施**（frontend/src/utils/ai.js、views/AiSettingsView.vue）
- 服务商：内置 DeepSeek（默认）、OpenAI、阿里云百炼、智谱 GLM、Kimi、硅基流动、Ollama（本地）及“自定义地址”（任意 OpenAI 兼容接口）。
- 配置项：接口地址 / API Key / 模型；开发模式经 Vite `/ai-proxy` 代理（仅默认 DeepSeek 地址生效）；Electron 生产模式直连；支持“测试连接”（仅发送测试串“OK”）。
- 本地历史：最近 50 条分析/报告记录存 localStorage，可一键清空；未配置 Key 时相关入口引导用户先到“我的 → AI 设置”配置。

### 1.3 AI 介入边界（本系统的设计红线）

1. **AI 不参与自动决策**：判分、权限校验、数据入库、统计计算均为确定性代码；
2. **AI 不直接修改业务数据**：所有 AI 输出先呈现给用户，人工确认后才可能进入预览/草稿流；
3. **AI 不是系统可用性的前提**：无 API Key 时练习、判分、错题、统计等全部核心功能不受影响；
4. **AI 不是数据收集器**：无隐式/批量/后台调用，无用户行为上报。

### 1.4 核心价值

- 对教师：把“补全答案解析、评估题目质量”从人工逐条处理变为批量 AI 草稿 + 人工把关，建库效率数量级提升；
- 对学生：基于本人真实练习数据获得个性化薄弱点分析与学习建议，解决“刷题无反馈”的普遍问题；
- 对部署方：模型与服务商**完全自选**——合规要求高时可接本地模型，实现“题目数据不出内网”，这是商业题库平台难以提供的 AI 治理能力；
- 对项目本身：AI 以“可插拔增强”方式存在，不绑架产品核心，也不引入黑盒风险。

## 2. 数据来源与合法性分析

### 2.1 系统内数据的来源渠道（事实）

| 渠道 | 说明 | 权属与合法性要点 |
| --- | --- | --- |
| 用户手工录入 | 在题目管理页逐题创建 | 内容由录入者提供并负责 |
| 用户批量导入 | Excel(.xlsx)/CSV（UTF-8/GBK）导入自有表格；模板由系统生成、**内容由用户提供** | 上传者须对其持有的内容有合法权利（自编、已获授权、或处于公有领域等） |
| 共享与拷贝 | 题目/题库在系统用户间共享；拷贝副本记录来源字段（origin_bank_id），订阅可实时跟随 | 系统内流转，权限模型控制范围（只读/可编辑），可溯源 |
| 演示数据 | db/init.sql 种子数据（admin/demo 演示账号与示例题目） | 团队自行编写，无第三方内容 |
| 练习行为数据 | 用户本人的练习/判分/错题/收藏记录 | 用户本人操作生成，仅本人与管理员（统计视图）可见 |

系统**不内置任何第三方版权题库，不含爬虫采集，无内容市场**——从架构上规避了版权内容风险，这也是产品的刻意定位。

### 2.2 个人信息与敏感数据处理（现状事实）

- 系统采集的用户字段仅为账号类基础信息（用户名/昵称/邮箱/头像/密码哈希），无身份证号、无学号强绑定、无地理位置等敏感信息；教育场景落地时建议进一步最小化（例如允许关闭邮箱必填）【产品待办】。
- 题目内容中若包含个人信息（如试卷中出现学生姓名），由上传者自行把关；系统文档建议导入前脱敏【使用提示，建议在产品内补充】。
- 练习与统计数据的访问控制：数据按用户隔离，管理员可看全站统计；共享仅限用户主动发起且权限可见可撤。

### 2.3 发送给大模型的数据及其合法性边界

**发送原则（代码事实）**：仅在用户点击“补全/分析/报告”时，发送**当次任务所需的最小文本**：

- 场景 A/B：当前题目文本（题干/选项/标签/参考答案/解析）——均为**该用户自己录入或合法导入、且本人有权限查看的题目**；
- 场景 C：数字型统计摘要 + 分类名称，不含用户名、密码、邮箱等账号字段；
- 不发送：数据库凭据、其他用户的数据、API Key（Key 仅用于用户浏览器直连时的请求鉴权，由浏览器直接提交给服务商）。

**合规要点**：
1. 模型调用发生在**用户浏览器与服务商之间**，本项目后端不中转、不落盘 AI 请求/响应；
2. 由用户自行注册并遵守其选择的服务商服务条款与数据处理政策；支持境内服务商（DeepSeek、通义、GLM、Kimi 等）与本地模型（Ollama，数据不出本地/内网）；
3. 若部署主体涉及未成年人数据处理，建议按《个人信息保护法》关于未成年人信息的规定取得监护人同意并最小化收集（部署者义务，非本开源工具自动承担）；
4. 正式商用/试点时，建议由部署单位就“数据出境、第三方模型数据处理、用户协议与隐私政策”出具书面评估【占位：法律意见/隐私政策文本】。

### 2.4 存储与删除

- 业务数据存储于部署方自己的 MySQL（私有化部署，数据主权归部署者）；
- AI 配置与历史仅存用户浏览器 localStorage（最近 50 条），设置页提供一键清空；题目删除/用户删除由系统常规删除流程处理，无 AI 专用留存副本。

## 3. 算法可解释性说明

### 3.1 总体立场

本系统**不训练自有模型、不进行黑盒决策**。AI 的定位是“可审计的辅助内容生成”。系统的可解释性分三层，均可在开源代码中核查：

### 3.2 第一层：核心业务逻辑与 AI 完全解耦（确定性、可复现）

| 业务 | 实现（源码可查） | 可解释性 |
| --- | --- | --- |
| 自动判分 | backend/src/main/java/com/qbank/util/QuestionGrading.java | 规则明确：单选/多选/判断精确匹配；填空多空以分隔符分隔逐空判定；简答宽松匹配（忽略空白/大小写等）。同输入必同输出，附单元测试 |
| 权限与会话 | JWT + 服务端白名单（AuthInterceptor、JwtTokenManager） | 标准算法（HMAC 签名、7 天有效期、登出即失效），行为可预期 |
| 统计指标 | StatsService 等 | 正确率/趋势/Top5 均由 SQL 聚合计算，口径见接口文档与源码 |
| 抽题/随机 | 随机模式抽题（避免全表 ORDER BY RAND 的优化实现） | 无个性化隐式排序，仅随机性 |

### 3.3 第二层：AI 调用透明化（提示词与调用点公开）

- 三个场景的提示词为**固定模板、硬编码于开源仓库**（frontend/src/utils/ai.js 的 `buildQuestionPrompt`/`buildReportPrompt` 与 ImportDialog.vue 的补全提示词），输出结构被明确约束（分点编号 / 纯 JSON 对象），审查者可逐字核对“系统向模型提了什么要求”；
- 模型选择、接口地址、调用时机、失败提示均对用户可见（“AI 设置”页可测试连接并查看历史）；
- 每次生成记录本地历史（时间、模型、类型），用户可回看或一键清空。

### 3.4 第三层：人对结果的最终解释权（Human-in-the-loop）

- 补全结果 → 仅写入可编辑预览 → 人工核对 → 入库；
- 质量分析/学情报告 → 仅展示（弹窗/历史），不触发任何业务变更；
- 失败兜底 → 明确提示“AI 未能补全…可手动补充”，不静默产生错误数据。

### 3.5 关于模型本身“不可解释”部分的边界说明

第三方大模型内部推理过程不可解释、输出具有一定随机性，这是当前生成式 AI 的客观技术边界。本系统的应对不是“声称可解释”，而是**结构性规避**：AI 永远不承担事实判定、评分、权限等需要解释与追责的职能；其输出属于“建议文本”，差异不改变任何业务数据。若未来规划“AI 自动组卷/自动评分”等职能性功能，须另行设计可解释与人工复核机制（见第 5 章）。

## 4. AI 伦理风险评估

评估方法：团队基于产品形态（开源、自托管、教育场景、AI 辅助定位）逐项识别，给出风险等级（低/中/高，为团队主观评估）与缓解措施。**残余风险均需部署方在真实环境中确认。**

| # | 风险 | 等级 | 风险说明 | 现有缓解（代码/产品事实） | 残余风险与建议 |
| --- | --- | --- | --- | --- | --- |
| R1 | 内容幻觉与错误 | 中 | 大模型可能生成错误答案/解析或错误学情判断，教育场景有误导可能 | 补全仅进预览且可人工编辑、失败行显式提示；质量分析提示“不要直接给出完整答案”；AI 不参与判分；判分为确定性规则 | AI 建议仍需使用者复核。建议：正式场景发布“AI 结果仅供参考、以教师核定为准”的界面提示【产品待办】 |
| R2 | 隐私与密钥安全 | 中 | API Key 存 localStorage 存在本机泄露面；题目文本可能含个人信息并被发送至第三方 | Key 不经本项目服务器；仅用户触发时发送最小化内容；支持本地模型；历史可一键清空 | 公共电脑使用后应清理；Key 泄露风险由服务商侧管理。建议：文档增加风险提示、提供“使用后清理”指引【文档待办】 |
| R3 | 偏见与公平 | 低 | 模型建议可能存在偏见 | AI 不产生评价性结论（不评分、不排名、不筛选），学情报告仅建议性文字且基于用户本人数据 | 若用于班级横向比较需人工判断；报告无横向对比功能 |
| R4 | 过度依赖与学术诚信 | 低 | 学生可能依赖 AI 补全答案跳过思考；练习时作弊 | 练习过程不显示答案（防作弊设计）；质量分析提示词禁止给出完整答案；补全发生在教师导入环节而非学生练习环节 | 学生自带 Key 也能分析单题——属通用大模型能力，无法在工具层完全禁止；建议使用场景由教师/家长管理 |
| R5 | 第三方服务商依赖与数据出境 | 中 | 模型能力、可用性、数据处理政策取决于用户所选自第三方；境外服务商可能涉及数据出境 | 多服务商可选、架构无绑定；本地 Ollama 支持实现数据不出内网；境内服务商为默认 | 出境/合规判断属部署主体责任【建议正式部署前出具专项意见】 |
| R6 | 提示注入与恶意内容 | 低 | 题目文本作为提示词一部分，极端情况下可构造恶意输入影响输出 | 输出被限制为文本展示或需人工确认的预览，不执行、不写库、无插件机制；系统内无代码执行面 | 内容审核责任在部署方；建议共享题目时启用人工审核（规划） |
| R7 | 责任边界不清 | 中 | AI 建议引发后果时责任归属可能模糊 | 产品层：AI 不决策、人工确认链完整、开源可审计；文档层：明确“AI 输出为建议” | 部署/商用前需用户协议与免责条款【占位】 |
| R8 | 未成年人保护 | 中 | 若面向中小学，涉及未成年人数据与内容适宜性 | 系统默认面向可自主操作的成年用户/高校场景；数据字段最小化；无社交化功能 | 中小学部署需监护人同意机制与内容审核流程（部署方义务）【评估占位】 |

**风险小结**：本系统 AI 介入被刻意设计为“低权限、弱职能、人工兜底”，因此高等级自动决策类伦理风险（自动评分、自动淘汰、生成内容直发学生等）在架构上不存在；中等级风险集中在内容质量（R1）与第三方数据合规（R2/R5），通过“人工确认 + 服务商自选 + 本地模型选项”缓解，残余风险由使用方按场景确认。

## 5. 合规性声明与建议（一般性提示，非法务意见）

1. 当前形态：本开源项目是**通用软件工具**，向部署者提供接入第三方大模型接口的客户端能力，本身不运营模型、不向公众直接提供生成式 AI 服务、不存储 AI 对话。因此不构成《生成式人工智能服务管理暂行办法》意义上的“面向境内公众提供生成式 AI 服务”的提供者——但该判断需结合最终运营形态确认。
2. 若未来团队以 SaaS 形态对外运营（内置模型服务、面向公众开放），将触发生成式 AI 服务的安全评估、备案（含算法备案如涉及）等义务，须在运营前完成【占位：专项合规工作项】。
3. 个人信息：《个人信息保护法》《数据安全法》要求处理个人信息须有合法依据并采取安全措施；教育场景涉及未成年人信息时适用更严格规则。开源工具本身不自动履行部署者的合规义务，建议部署单位完善隐私政策、用户协议与数据安全管理制度【占位】。
4. 数据出境：若选用境外模型服务商并传输境内个人信息/重要数据，需按数据出境相关法规评估（默认推荐境内服务商与本地模型可规避）。
5. 建议在正式申报、试点或商用前，由团队咨询学校法务或专业机构并留存书面意见【占位】。

## 6. 结论

本系统以“前端本地直连、Key 用户自持、输出人工确认、AI 不决策”四原则接入大模型，在获得建库效率与个性化反馈价值的同时，将 AI 相关数据、隐私、可解释与伦理风险控制在可审计、可规避的范围。AI 是增强而非核心，核心闭环（管题—练习—判分—统计）完全脱离 AI 亦可运行，符合教育场景对稳定与可解释的底线要求。
